## 3. 目標 1：讓錯誤一定在執行時被抓到

### 3.1 -O1 為什麼會把錯誤「優化掉」，改回 -O0 為什麼不夠

C++ 把越界、溢位、除以零、空指標、缺 return 都定義為未定義行為（undefined behavior，UB）。編譯器可以假設 UB 不會發生，並據此刪改程式。預期會看到（S0 驗證）：

- 缺 return 的函式：clang 在 -O0 放一個 trap，在 -O1 把那條路當成走不到而刪掉，函式默默回傳別的值。
- `7 / 0` 這種兩邊都是常數的除法：編譯時就被折成無意義的值，不會 trap。
- `for (int i = 1; i > 0; i *= 2)`：-O1 可以假設 `i` 不會溢位，條件永遠成立，變成無窮迴圈。

改回 -O0 只解決第一類。越界、空指標、溢位在 wasm 裡本來就沒有硬體檢查：讀位址 0 會成功（`--stack-first` 讓位址 0 落在棧底，11-05 紀錄 §5），越界寫入會寫進相鄰的變數，溢位直接繞回。而且 -O0 會讓瀏覽器遞迴深度從 3,734 層掉回 463 層。所以作法不是換最佳化等級，而是**在程式裡插入檢查**，保留 -O1。

### 3.2 三層偵測

**A 層：編譯器插入的檢查（clang 的 UndefinedBehaviorSanitizer，UBSan）**

- 旗標：`-fsanitize=undefined -fno-sanitize=vptr,function`。clang 在產生程式碼時（最佳化之前）就在每個危險運算前加一個判斷，判斷成立就呼叫處理函式。這個呼叫有副作用，最佳化只能在證明判斷永遠不成立時刪掉它，也就是該錯誤確實不可能發生的時候。例外是程式在更早的地方已經有一個沒被檢查到的 UB（例如讀取未初始化的變數），最佳化可能據此推出錯誤的結論；這也是 C 層要補未初始化檢查的原因。
- 處理函式不需要 compiler-rt（瀏覽器版工具鏈沒有）：在新檔 `vgerr.h` 自己實作約 20 個 `__ubsan_handle_*`（參數格式見 compiler-rt `ubsan_handlers.h`），和 `vg.h` 一起強制引入。
- 本機試跑（2 個案例，見 §8 的偏差說明）：連結成功，不需要新的 WASI import；除以零回報 `{"vgerr":"div-by-zero","line":6,"col":103,"lhs":7,"rhs":0}`。
- 涵蓋：整數除以零與 `INT_MIN / -1`、有號溢位（`+ - * ++ --` 與負號）、位移量錯誤、固定大小的陣列越界（含二維）、空指標解參考與成員存取、缺 return、`__builtin_unreachable`、VLA 長度 ≤ 0、浮點轉整數超出範圍、指標運算溢位、bool/enum 非法值。
- 位置：行號就是原始行號（插樁只插入文字、不改行數，`instrument.js:1240` 會檢查）。欄號是插樁後的欄號，要由插樁器回傳每行的插入位置換算回原始欄號（新增）。
- 運算元：處理函式拿得到實際的值（`a = 7, b = 0`；`int[5]` 的索引 5；溢位前的兩個運算元），圖解直接使用。

**B 層：標準函式庫的檢查（libc++ hardening）**

- 旗標：`-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_EXTENSIVE`。
- 涵蓋（libc++ 19 標頭中的檢查）：vector／deque／string／array 的 `[]` 越界；空 vector 的 `front`、`back`、`pop_back`；空 deque 的 `front`、`back`、`pop_front`、`pop_back`（stack 的 `top`/`pop`、queue 的 `front`/`pop` 都走 deque）；`erase` 範圍錯誤；比較函式不合法時 `sort`／`nth_element` 會讀出界的情況。
- 問題：EXTENSIVE 模式失敗時只執行一個 trap，訊息只存在除錯資訊裡。解法：替換 libc++ 留給廠商客製的 `include/c++/v1/__assertion_handler`（放進 `headers.tar`，掛載時覆蓋 sysroot 的版本），改成呼叫 `vgerr.h` 的函式並帶上訊息（例如 `vector[] index out of bounds`）。檔案已寫好：`experiments/runtime-error-s0/assertion_handler.h`。
- 不用 DEBUG 模式：它在 `sort` 之後會用使用者的比較函式再檢查一遍（`__debug_utils/strict_weak_ordering_check.h`），還把比較函式包一層、多呼叫一次（`__algorithm/comp_ref_type.h:57–59`）。使用者自己寫的比較函式有插樁，多出來的呼叫會變成額外的停點，軌跡就多出學生程式本來沒有的步驟，和不加檢查時不同。S0 的 `sandebug` 設定會量出這個差異。
- `-fno-exceptions` 下的 `at()`、`substr()`、`stoi`、`bad_alloc` 會呼叫 `__libcpp_verbose_abort`（`stdexcept:218–250`）。`vgerr.h` 覆寫它，取得 `out_of_range was thrown ...` 這類訊息。本機試跑確認覆寫可行（vector 越界案例，當時用的是 DEBUG 模式）。
- 限制：libc++ 的訊息沒有索引值、也沒有學生的行號。行號取軌跡的最後一步。至於是哪一個 `[]`、索引是多少，第一版用「該行所有下標以停點的變數值求值」推斷（`localgdb/expr.js` 已能求值）；推斷不準時，再改由插樁器包住容器下標（P4）。

**C 層：執行環境與其他**

- 已有：wasm trap、8 MiB 棧溢位、逾時、輸出上限、步數上限。修正 §2 的分類錯誤（多數情況 A 層會先抓到）。
- `assert`：覆寫 `__assert_fail`，帶出條件式的文字。
- 堆積：在 `vgerr.h` 取代全域 `operator new/delete`，記錄每個配置區塊，可以準確抓到重複 `delete`、`delete` 不是 `new` 來的指標、`new[]` 配 `delete`，以及結束時沒有釋放的區塊（洩漏）。`delete` 之後再讀寫（use-after-free）需要檢查每一次記憶體存取，這套工具鏈沒有 AddressSanitizer，所以抓不到；只能在釋放時填入特殊值並暫時不重用，讓軌跡出現可疑值，圖解標「可能」。
- 迭代器失效：libc++ 19 沒有追蹤迭代器失效的檢查，這一版抓不到，圖解頁註明限制。
- 未初始化：D6 已經在每一步標出未初始化的變數。新增「讀取時檢查」：插樁器替宣告時沒有初始值的變數加一個旗標，寫入時設為已初始化，讀取時檢查。規則保守：可能漏報，不會誤報。
- 無窮迴圈：碰到步數上限時，檢查軌跡是否出現完全相同的狀態（同一行、同一個 frame、所有變數值相同）。有就判定為無窮迴圈並指出循環；沒有就只說「步數超過上限」。
- 無窮遞迴與遞迴太深：堆疊溢位時看軌跡的呼叫鏈。參數一直往同一方向走、從沒碰到終止條件，判定為無窮遞迴；否則是瀏覽器的限制。兩種都改成可以回放到最後一步。
- 提醒（不是 UB，不中止）：`cin` 讀取失敗（`vg.h` 每一步檢查 `cin` 狀態有沒有變化）、無號數繞回（`-fsanitize=unsigned-integer-overflow`，只套用在學生的程式碼，標頭用 ignorelist 排除）、浮點除以零（得到 inf/NaN）。

### 3.3 錯誤發生之後（決定 2：分流，2026-11-23 已選定）

| 處理 | 錯誤 | 理由 |
|---|---|---|
| 停在那一行，程式結束 | 除以零、空指標、容器越界與空容器操作、缺 return、assert、abort、堆疊溢位、bad_alloc、重複 delete | 原生 Linux 也會崩潰或中止；libc++ 的檢查失敗後無法繼續 |
| 在那一步跳出圖解並暫停，可繼續單步 | 有號溢位、位移量錯誤、C 陣列越界、浮點轉整數超出範圍、指標運算溢位 | 原生常默默繼續；學生可以看到溢位後的值、被蓋掉的相鄰變數 |

可繼續的錯誤，同一個位置只報一次，整次執行設上限。C 陣列越界寫入之後的結果取決於變數在記憶體中的排列：結構成員的排列由 C++ 規則決定，與環境無關；各自宣告的區域變數，wasm 與 g++ 的排列可能不同，圖解要註明環境差異（11-05 決定）。

### 3.4 引擎資料流的改動

- `vgerr.h`（新）：處理函式在 fd 3 寫一筆錯誤紀錄，例如 `{"err":"div-by-zero","line":6,"col":13,"v":{"lhs":7,"rhs":0}}`。S0 的版本暫時寫到 stderr。
- `trace.js`：接受錯誤紀錄（固定欄位、kind 白名單、line 範圍、值只能是數字或短字串、筆數上限），掛在最後一個停點上。學生程式可以偽造錯誤紀錄，影響只限自己的畫面，與現有停點紀錄的殘餘風險相同（engine README Threat model M3）。
- `runProgram` 結果新增 `runtimeErrors: [{kind, step, line, col, fatal, values, libcxxMessage?}]`。
- `pipeline.worker.js`：編譯旗標、PCH 旗標，以及 PCH 金鑰（`PCH_FLAGS_VERSION` 改版）。`scripts/build-assets.mjs`：把 `vgerr.h` 與替換的 `__assertion_handler` 打進 `headers.tar`。
- `localEngine.ts`：`mapRunError` 不再把 stack-overflow、step-limit 當成不能回放。
- LocalGdb：致命錯誤沿用 signal stop（SIGFPE 等），多帶一個欄位指向 `runtimeErrors`。可繼續的錯誤在播到那一步時比照斷點停下。
- 不動：`LINK_FLAGS`、`--stack-first`、守衛區。

### 3.5 要量的代價（S0）

- 編譯時間：預算 8 秒（上限 9.5 秒）。本機試跑沒有 PCH 時編譯 4.1–6.4 秒，那不是 lab-david 的數字。S0 比較 `plainpch` 與 `sanpch`。
- PCH：檢查旗標要編進 PCH，學生第一次使用時會重建（PCH 上限 30 秒）。
- wasm 大小、執行時間。
- 遞迴深度：檢查會讓每層函式變大。S0 在 1 MB 的 worker 棧比較加檢查前後；瀏覽器數字要另外用 `tests/engine/browser/recdepth.html` 重量。
- 軌跡一致性：沒有錯誤的程式，加檢查前後的停點與輸出必須完全相同。S0 的 `fidelity` 跑 22 個 E3 程式和 `examples/` 裡所有教案。這正是 2026-11-04 決定不改引擎的理由之一，所以列為通過條件；它也會列出本來就含 UB 的現有教案。

## 4. 目標 2：每一種錯誤的圖解

### 4.1 共同規則

- 架構照編譯錯誤視覺化的三層：解析（錯誤紀錄）→ 分類（家族與子類型）→ 畫面（一個子類型一個畫面），原始訊息收合在底部；用白話，術語放括號（`CompileDiagView.tsx` 的做法）。
- 每個畫面分三段：
  1. **發生了什麼**：一張圖，值全部來自這次執行（錯誤紀錄＋軌跡），不寫死。
  2. **值從哪裡來**：出問題的值最後一次在哪一步、哪一行被寫入；點一下跳到那一步。軌跡有完整歷史，`cellWrite.js` 已能找陣列格子的最後一次寫入。
  3. **怎麼改**：一句話加上改好的寫法。
- 顏色代表狀態（設計系統）：只有出錯的元素用紅色。
- 記憶體排列圖一律標「示意」，只畫相對位置，不畫絕對位址（11-05 決定）。
- 與原生 Linux 結果不同時要明說（11-05 決定），例如 vector 越界在原生常默默繼續，IRIS 會停下。
- 引擎限制（瀏覽器遞迴深度、步數上限、逾時）用另一種標題：「這不是程式的錯，是瀏覽器引擎的限制」。學生的錯不怪到引擎上，引擎的限制也不怪到學生身上。
- 沿用既有元件：容器格子（`ContainerVisualizer`）、呼叫歷史圖（`CallGraph`）、UML 物件圖、區間尺規（`RangeRuler`）、步驟表。

### 4.2 圖解目錄

偵測欄的 A/B/C 對應 §3.2；「停」與「續」對應 §3.3。

**家族 1：數值**

| 子類型 | 偵測 | 停/續 | 主圖 | 值從哪裡來 |
|---|---|---|---|---|
| 整數除以零 | A | 停 | 算式卡：`a / b` 底下標出 a = 7、b = 0（紅） | b 最後一次變成 0 的那一步 |
| INT_MIN / -1 | A | 停 | 數線：int 範圍的兩端，正確結果 2147483648 落在右端外面 | 兩個運算元的來源 |
| 有號溢位 | A | 續 | 位元格（你在 11-05 選的方案 B）：32 格位元，上排是數學上的正確結果，下排是實際存進去的值，進位跑進符號位；旁邊的數線標出 INT_MAX | 運算元的來源；繼續後「這一行之後」面板顯示繞回的值 |
| 位移量錯誤 | A | 續 | 32 格位元條，位移量超過 31 時整條被推出框外 | 位移量的來源 |
| 浮點轉整數超出範圍 | A | 續 | 數線：double 的值落在 int 範圍外 | 該 double 的來源 |
| 無號數繞回（提醒） | C | 續 | 時鐘式的環：0 再減 1 變成 4294967295；常見於空 vector 的 `v.size() - 1` | 容器變空的那一步 |
| 浮點除以零（提醒） | C | 續 | 結果 inf 或 NaN，加一句說明 | 除數的來源 |

**家族 2：陣列與容器**

| 子類型 | 偵測 | 停/續 | 主圖 | 值從哪裡來 |

### 9.4 發現的既有問題：建構子的成員初始化清單裡的停點

- 插樁器把停點插在成員初始化清單（member initializer list）裡，例如 `PVec(int n):m_pts((__vg::pushFrame(), __vg::step(..., __vg::v("this", *this), ...), n))`。這一步會拍下整個 `*this`，但此時 `m_pts`（vector）還沒建構。
- 拍照時要走訪 vector 的起點到終點，這兩個指標還是記憶體裡的殘值，結果走訪一段任意長度的記憶體。
- 正式機流程：5 秒後被強制結束，0 步、沒有輸出，所以線上這兩課現在跑不動。不設 5 秒限制時，約 8～9 秒後程式中止（abort，多半是記憶體不夠）。加檢查時，55 ms 就在 libc++ 的 `__iterator/wrap_iter.h:50` 回報「把參考綁到空指標」。
- 同一個機制也造成 9.3 的 338 筆成員值差異；只有成員是容器時才會卡死。
- 修法（待決定）：成員初始化清單裡的停點不要拍還沒建構的成員，或在建構子本體開始前不拍 `this`。

### 9.5 對設計的影響

- 回報要帶檔名。CC-2607A 的回報位置是 libc++ 標頭的第 50 行，沒有檔名時看起來像學生程式的第 50 行（學生程式只有 48 行）。不在學生程式的位置，畫面一律改用軌跡最後一步的行號，並寫「在這一行呼叫的函式庫裡」。
