# 快轉指導 `[fast @N]` Design

**Date:** 2026-07-29
**Status:** Draft, pending user review
**Affects:** `VisualizerHelper.js`（TTS 指令解析 / play_tts）、`GdbApi.tsx`（快轉時繞過 for 虛步）、新增共用 `anim.ts`、`AUTHORING_GUIDE.md`
**目標：** 讓教案能無聲快轉過前面幾圈迴圈，停在指定的第 N 次造訪，用來快速展示教案的不同段落。

## 語法

寫在 `@tts` 最前面，屬於現有的 `[指令]` 前綴家族（AUTHORING_GUIDE §3.4）：

```cpp
for (int i = 0; i < n; i++) {   //@ @tts [fast @{n}] 這是最後一圈了，i={i}
```

`@N` 可以是常數（`[fast @5]`）或 `{變數}`（`[fast @{n}]`，沿用 §3.2 的即時取值）。

**同一行的 TTS 文字就是抵達後要講的話。** 快轉的終點與終點旁白寫在同一處，不需要兩地維護。抵達後 `[fast @N]` 的行為等同 `[next]`——唸完該行文字後步進下一行。

## 語意

`[fast @X]` 出現在第 L 行時：

- **武裝**：停在第 L 行且 `__line_visit_count[L] < X` → 進入快轉模式。
- **快轉模式期間，每一個停駐點都靜音**——不發 TTS、不等停頓、動畫零延遲，立刻自動步進。
- **解除**：停在第 L 行且 `__line_visit_count[L] >= X` → 離開快轉模式，該行照常唸出它的 TTS。

終點條件綁在 (行號, 次數) 上，但**抑制範圍是全域的**。這點是設計核心：若只讓第 L 行安靜，迴圈本體的每一行還是會照唸，等於沒有快轉。

次數沿用既有的 `__line_visit_count`（`Actions.ts:85`），與 `@N` 門檻同一個計數器，**從程式開始累計**。因此一個被呼叫兩次的函式，其內部迴圈在第二次呼叫時計數不會歸零——`[fast @3]` 只會在第一次呼叫的第 3 圈生效，之後不再快轉。這是使用者明確選擇的行為。

## 前置條件（已完成）

使用者提出的兩個顧慮，其一已修：`0661a40` 修掉了 BST 樹形會被重建成排序後退化鏈的競態。這是快轉的**前置條件**——快轉的全部價值是「落地時狀態正確」，樹形若可能被改成鏈，快轉做完畫面仍不可信。

其二不修、屬既有行為：按 ⟲ 重新執行時 `__line_visit_count` 會歸零（`Actions.ts:84`），所以快轉會**再武裝一次**。展示時每重跑一次就要再付一次快轉時間。這無法避免——程式狀態必須從頭重建。同一次執行內迴圈再次進入則不會重複快轉，因為計數是累計的。

## 狀態保真

快轉期間**照樣逐行步進**，所以 `diffOps`、呼叫圖、`__line_visit_count` 全部照常累積。落地時樹、呼叫圖、`@N` 門檻都是正確的，不會出現「跳完發現容器是空的」。

動畫不跳過、只是零延遲：新增全域旗標讓各 plugin 的 `delay()` 直接返回。BST history 與最終畫面跟慢慢走完全一致。

**已知成本：** 每一步是一次 GDB round trip（約 10–50ms），跳 1000 步約 10–50 秒。這是保真的必然代價。需要跳幾千步的場景應改用斷點 + `[continue]`，接受狀態由單次 diff 補上。

## 求值時機與教案撰寫規則

`{變數}` **只在武裝當下求值一次**，之後固定不變。

**硬性規則（違反會導致快轉停不下來）：** `@{變數}` 的值必須在進入該函式或迴圈**之前**就已決定，且不得與該區塊內會變動的數字相關。

- ✅ `for (int i = 0; i < n; i++)` 搭配 `[fast @{n}]` —— `n` 在迴圈外決定
- ❌ `[fast @{i}]` —— `i` 是迴圈變數，武裝當下是 0，永遠不會等於它自己
- ❌ `[fast @{sum}]` —— `sum` 在迴圈內累加

求值失敗（變數不在 scope、無法解析成正整數）時**不武裝**，退回 `[next]` 行為，並在 console 留下警告。教案照常播放，只是沒有快轉——失敗模式是「沒快轉」而非「壞掉」。

**求值成功但目標次數永遠達不到**（迴圈提早結束、或 `X` 大於實際圈數）時無法事先偵測：快轉會繼續無聲衝過教案剩餘的部分，直到 5000 步上限或程式結束才解除。這是上述硬性規則的直接後果，也是設 5000 步上限的主要理由。

## 只在自動播放生效

`autoplay_enabled` 為假時 `[fast @N]` 完全不武裝，行為等同 `[next]`。手動按下一步卻一口氣衝掉兩百步太突兀，而且這個功能的用途是展示。

## 與 for 三段式單步的互動

`5975690` 加入的 for A/B/C 虛步會攔截 `click_next_button`。快轉期間必須**繞過它**，否則每個 for 行要多花一個虛步、B 高亮還會閃爍。快轉模式下 `for_sub_step` 一律設為 `null`、不攔截。

## 安全上限

快轉模式維護一個步數計數器，超過 **5000 步**強制解除並在 console 警告。沒有這個上限時，一個打錯的 `@{變數}` 會讓教案永遠停不下來，而使用者在展示現場沒有辦法中止。程式結束（`inferior_program_exited`）與重新執行時也一律解除。

## 架構

1. **`parseFastDirective(ttsText)`** —— 純函式，回傳 `{ target: string } | null`，`target` 是尚未求值的 `@` 引數（`"5"` 或 `"{n}"`）。與現有 `[next]` 等指令的解析放在一起（`VisualizerHelper.js:402` 附近）。
2. **`decideFastState(line, visitCount, armed)`** —— 純函式，回傳 `'arm' | 'hold' | 'disarm' | 'none'`。所有次數判斷邏輯集中在這裡，可單獨測試。
3. **快轉模式狀態** —— `global_variable.__fast_forward = { line, target, steps } | null`。
4. **共用 `delay()`** —— 目前 `BSTPlugin` / `LinearPlugin` / `MazePlugin` 各有一份重複的 `delay()`。抽到新的 `gdbgui/src/js/anim.ts`，內含快轉時直接返回的判斷。這是重複程式碼的既有問題，剛好在要動的路徑上，順手收斂。

## Scope / 非目標

- 不做 `[fast-to:行號]` 或 `[fast:N步]`——使用者要的是造訪次數，不是行號或步數。
- 不做手動模式的快轉。
- 不改 `@N` 門檻語意、不改 `__line_visit_count` 的計數方式。
- 不做快轉中途的中止 UI（5000 步上限即為保險）。

## 驗證

**單元測試（`gdbgui/src/js/tests/fastForward.jest.ts`）**

1. `parseFastDirective`：`[fast @5]` → `"5"`；`[fast @{n}]` → `"{n}"`；`[next]` → `null`；`[fast]` 無引數 → `null`。
2. `parseFastDirective` 與 `|` 多段、`@N` 門檻混用時只解析被選中的那一段。
3. `decideFastState`：未武裝且 `count < target` → `arm`；已武裝且非目標行 → `hold`；已武裝且目標行 `count >= target` → `disarm`；未武裝且 `count >= target` → `none`（不武裝，直接正常播放）。
4. 步數上限：`steps > 5000` → `disarm`。

**e2e（`e2e/tests/zz_fast_forward.spec.ts`）** —— 一個跑 5 圈的迴圈教案，`[fast @4]` 寫在迴圈行：

1. 落地時 `paused_on_frame.line` 是迴圈行，且 `__line_visit_count[迴圈行] === 4`。
2. 快轉期間**沒有任何 TTS 字幕出現**（觀察 `tts_subtitle` 未變動）。
3. 落地時容器狀態正確（前 3 圈 push 進去的元素都在）——這是「保真」的實測，也是本設計與 `[continue]` 的差別所在。
4. `autoplay_enabled` 為假時，同一份教案按下一步只前進一行（不武裝）。
