# 設計：經過的指導行一律畫出來（靜默通過 `[continue]`）

日期：2026-10-30
狀態：草案，待使用者核准（HARD-GATE：核准前不寫產品程式碼）

## 意圖與為什麼

目前畫面只在 GDB 停下來的那一刻才更新。程式若經過了某一行、那行帶有指導（字幕、TTS、
圖形指令），但 GDB 沒有停在那行，這行的畫面就不會出現。

使用者要的規則：**指導有經過，就要畫出來。** 不是「停在某行才畫」。

已確認的兩條路徑與決定：

| 路徑 | 現況 | 決定 |
|---|---|---|
| `[continue]` 自動播放 | 直接跑到下一個斷點，中間的指導行不停駐、不畫 | **要改**。經過的指導行靜默畫出（不播 TTS、不停留） |
| `[next]` / `[step-out]` 自動播放 | `next` 跨過函式呼叫時，被呼叫函式內的指導行不停駐；`step-out` 同理 | **要改**（使用者決定 A：要）。需要追蹤呼叫深度，見「第 1.5 節」 |
| `[fast @N]` 一次跳 | 中間停駐點靜音吃掉，只在落地時 refresh | **不改程式**。使用者確認「只要最後停在正確狀態」，現有設計已滿足 |

## 目標

- 自動播放遇到 `[continue]` 時，程式在中間經過的每一行指導，都會更新畫面（圖形、容器、
  呼叫圖、`__line_visit_count`），但**不播 TTS、不停下來等使用者**。
- 過程結束後，畫面狀態與逐行走完（逐行 `next`）的結果一致。

## 非目標

- 不改 `[fast @N]` 的一次跳邏輯（落地狀態已正確）。
- 不改 `[step-in]` 的停駐行為（步入本來就會停在被呼叫函式的第一行）。
- `[next]` / `[step-out]` 的停駐行為**要改**：經過的指導行靜默畫出（決定 A）。
- 不改 TTS 播放、不改教案 JSON 格式、不改伺服器端。
- 不改使用者自己的斷點清單與 `frontend_*` 持久標記。

## 反目標（失敗定義）

- 靜默通過結束後，**遺留任何 GDB 臨時斷點**（每次必須清乾淨）。
- 靜默通過時**吃掉使用者的斷點**（使用者斷點所在行必須正常停下、照常播 TTS）。
- 靜默通過時**吃掉出題閘門**（題目行必須照常觸發測驗）。
- 靜默通過期間，使用者按暫停/關閉自動播放，卻仍一路續跑。

## 做法

### 1. 觸發條件

只在自動播放執行 `[continue]`、`[next]`、`[step-out]` 時啟用（`Actions.ts` 的 `play_tts`
解析出指令，或 `gdbgui_execute_autoplay_command` 送出）。手動按鈕不啟用，行為與現在相同。
`[step-in]` 不啟用（步入本來就停在被呼叫函式的第一行）。

### 1.5 `[next]` / `[step-out]` 的呼叫深度追蹤（決定 A）

這兩個指令的語意是「停在某個目標」，不是「跑到下一個斷點」：

- `[next]`：停在**同一個呼叫框架**的下一行。跨過的呼叫內部可能有指導行。
- `[step-out]`：停在**呼叫者**的下一行（`-exec-finish` 之後）。中途可能經過被結束的函式裡的指導行。

靜默通過時，GDB 會在這些中間指導行停下（臨時斷點），但**不能**就此續行，否則會衝過目標：

- 記下啟動時的框架深度（或框架位址）作為 origin。
- 靜默停在**更深**的框架（被呼叫函式內）→ 不可用 `-exec-continue` 盲目續行，必須保持
  「回到 origin 框架的目標行」這個終止條件。
- 靜默停在 origin 框架或更淺的框架 → 目標判斷與使用者斷點相同（下一行即停下、播 TTS）。
- 深度判斷與「目標行」的計算，**需要計畫階段的技術 spike 確認**，不能先假設 GDB 的行為。
  候選做法：在靜默期間用 GDB 原生的 `next` / `finish` 語意往前推，並以臨時斷點補足中間的指導行。
  spike 的結果若顯示做不到，這一項要回到核准流程，不能偷偷降級。

### 2. 臨時停駐點

啟用時，對教案中**所有帶指導的行**（`__line` / `__tts` / `__layout` 任一有內容）插入 GDB
斷點，使程式會停在每個指導行。斷點用 `-break-insert -f "<fullname>:<line>"`，記下回傳的
GDB 斷點編號。

- 已經是使用者斷點的行不重複插入。
- 通過結束（不論正常或異常）時，一律以記下的編號 `-break-delete` 清除。

### 3. 停駐點分類

每次停下時判斷：

- **是使用者斷點**（或出題閘門命中）→ 結束靜默模式，走現有 `inferior_program_paused`
  流程（含 TTS），行為與現在相同。
- **只是指導行（靜默）** → 執行畫面所需的步驟：
  - `__line_visit_count` 遞增、`__visited_lines` 記錄（決定 B：計入）
  - `recompute_for_sub_step`、`processing_guide`、`detect_container_op`、`detect_swap_call`
  - `refresh_state_for_gdb_pause`（取容器與區域變數）
  - **不呼叫** `play_tts`
  - 立刻送 `-exec-continue`（沿用出題重跑的「不播 TTS 直接續行」先例，
    `Actions.ts` 的 `isRerunningForQuiz` 分支）

### 4. 動畫零延遲

靜默步進期間動畫零延遲，沿用 `[fast @N]` 已有的全域旗標（各 plugin 的 `delay()` 直接返回）。
這符合「畫面跟著畫，但跑得快」。

- 零延遲只省掉等待時間，**動畫流程仍會執行**，每一步的 CPU 工作量沒有減少。
- 主要成本是每個靜默停駐的 GDB 往返與狀態刷新（快轉實測約 10–50ms/步），不是動畫本身。
  這點計畫階段要量測，不得以「不耗效能」當作既定事實。
- 每個 plugin 在零延遲下仍須得到與逐行走完一致的終態與 BST history（見
  `fast-forward-directive` 設計的「狀態保真」一節）。

### 5. 結束條件

- 停在使用者斷點 → 結束，正常播放。
- 程式結束 → 結束，清臨時斷點。
- 使用者暫停或關閉自動播放 → 結束，清臨時斷點，停在當前位置。
- 出題閘門命中 → 結束，交給既有出題流程。
- 不設步數上限（決定 C：不要）。迴圈內的指導行會一直畫，速度的代價由零延遲動畫與
  每步狀態刷新承擔。若實測太慢，要回頭討論，不得自行加上限。

### 6. 清理保證

所有結束路徑都走同一個 `finishSilentPass()`，負責 `-break-delete` 與重設旗標。
`inferior_program_exited` 也要呼叫它（與現有 `disarmFastForward()` 同一位置）。

## 元件（預計修改範圍）

- `gdbgui/src/js/VisualizerHelper.js`：新增靜默通過的純決策函式（停駐分類、是否續行），
  保持可單元測試。
- `gdbgui/src/js/Actions.ts`：`inferior_program_paused` 加入靜默分支；`inferior_program_exited`
  加入清理。
- `gdbgui/src/js/GdbApi.tsx`：新增插入/清除臨時指導斷點的命令產生函式（純函式，可測）。
- 新檔可能是 `silentPass.ts`，放純決策與命令產生；名稱在計畫階段定案。

**不動**：伺服器端、TTS 模組、教案資料格式、`[fast @N]` 模組。

## 測試與驗收

- **單元（Jest）**：決策函式的各分支（使用者斷點 / 指導行 / 閘門 / 結束 / 上限）；
  臨時斷點命令的產生與配對清除。
- **整合（e2e，依現有 `zz_*.spec.ts` 慣例）**：挑一個含 `[continue]` 且中間有指導行的教案，
  自動播放跑完後：
  1. 中間每個指導行的圖形/容器都有出現（可用 `__line_visit_count` 與畫面狀態檢查）。
  2. 最後停在的狀態，與同一教案用逐行 `[next]` 走到同一位置的狀態一致。
  3. 結束後 GDB 斷點清單只剩使用者原本的斷點。
- **回歸**：既有 `[fast @N]`、出題、`[next]` 相關測試須照舊通過。

## 已決定（使用者於 2026-10-30 回覆）

- **A. 要**：`[next]` 與 `[step-out]` 也要畫經過的指導。見第 1.5 節。
- **B. 要**：靜默經過的行計入 `__line_visit_count`。此變更會改變既有教案 `|@N` 與
  `[fast @N]` 對被 `continue` / `next` 跳過的行的計數行為，**須在測試中明確覆蓋**，
  並在最終報告列出受影響的教案。
- **C. 不要**：不設步數上限。

## 已知風險

- 每次靜默停駐都要一次狀態 refresh；長迴圈可能慢。不設上限（決定 C），以實測量測，
  超過可接受範圍時回頭請使用者決定。
- 臨時斷點與使用者斷點若在同一行，GDB 回報的 stop 可能只看得到一個編號；分類時要以
  「該行是否為使用者斷點」判斷，而不是只看 GDB 的 bkptno。
- 引擎是否為 GDB 或前端 wasm（見 `2026-10-05-remove-gdb-backend-design.md` 與 frontend-only
  cutover）會影響 `-break-insert` 是否可用。**計畫階段第一步要先確認引擎支援臨時斷點與
  `-exec-continue` 的停駐回報**，否則整個做法不成立。
