## 結論（一句話）

## 速度：最重要的發現

同一句 33 個字、Hanhan 語音，`rate` 與實際唸完時間：

| `rate` | 唸完時間 | 相對 `rate=1` |
| --- | --- | --- |
| 1 | 7.26 秒 | 1.00× |
| 1.5 | 6.51 秒 | 1.11× |
| 2 | 5.21 秒 | 1.39× |
| 2.5 | 5.21 秒 | 1.39×（**跟 2 一樣**） |
| 3 | 4.67 秒 | 1.55× |
| 4 | 3.75 秒 | 1.94× |
| 5 | 3.75 秒 | 1.94×（**跟 4 一樣，到頂**） |

- Chrome 把 `rate` 對應到 Windows 語音引擎的**整數檔位**，所以是階梯式的，而且上限約 1.94 倍。
- 想要「約 1.5 倍」要用 `rate = 3`，不是 1.5；現在的做法（`playbackRate = 使用者速度 × 1.5`）不能直接搬過來。
- 這個對應**每個語音、每個作業系統都不同**（macOS、Android 很可能是線性的），所以不能寫死。
- 標點符號的停頓不是主因：拿掉標點只省約 0.4～0.5 秒（`rate=1` 7.26 → 6.73 秒）。
- 其他中文語音在 `rate=1` 的速度相近：Yating 7.2 秒、Zhiwei 8.0 秒、Huihui 8.2 秒。

### 解法：靜音校準（已驗證可行）
把 `volume` 設成 0，讓瀏覽器對一句固定的短句用幾個 `rate` 各「唸」一次、量實際時間，就能建出這個語音的速度曲線，再挑出達到目標速度的 `rate`，存起來重用。**靜音量到的時間跟有聲完全一樣**：`rate=1`：7.27 秒（靜音）vs 7.25 秒（有聲）；`rate=3`：4.67 秒 vs 4.67 秒。代價是校準本身要花時間（每個 `rate` 約等於一句話的長度），可以用短句、只在第一次用某個語音時做、結果存在瀏覽器。

## 對正式設計的意義

1. **`[anim]` 用 `boundary` 事件對準文字位置**，不要把句子切成幾段分開唸：切段會多約 120 ms 的間隔，還會打斷語調。`word` 邊界事件給 `charIndex`，`[anim]` 標記在文字裡的位置對應到第一個 `charIndex ≥ 標記位置` 的事件。
2. **`[wait:N]` 用計時器**，不靠語音。
3. **速度**：用靜音校準建曲線，UI 的「1.0x」定義成「校準後約 1.5 倍於該語音的預設速度」，並且不超過該平台的上限。
4. **語音選擇**：優先 `zh-TW` 本機語音，其次 `zh-CN`；都沒有（例如某些 Linux）就只顯示字幕。
5. **語音清單要輪詢**：第一次呼叫 `getVoices()` 常回傳空陣列，`voiceschanged` 事件不一定觸發（我的測試頁就因此卡住過），要輪詢到有值為止。
6. `speak()` 需要使用者先操作過頁面（Chrome 的規定）；產品裡「按 Run」本身就滿足。
7. 不再需要伺服器的 `/tts_audio`、`gTTS`，也不會再有「伺服器呼叫 Google 翻譯的非官方語音」這個外部依賴。

## 沒做／沒驗證的

1. **聲音品質與發音**：我聽不到。`dp`、`nxt`、`dp[i][j]`、數字這些念得對不對、聽起來清不清楚，需要你用頁面上的「只念幾句教案旁白」按鈕聽聽看。
2. **只測了 Windows ＋ Chrome ＋ 本機 Microsoft 語音。** macOS、iOS、Android、Linux、Firefox、Safari 都沒測；Chrome 有網路語音（Google）時行為可能不同（例如長句可能被截斷，我在這台機器上沒有這種語音）。
3. 分頁在背景，雖然時間看起來正常，前景的數字可能略有不同。
4. 沒有把校準做成完整流程，只驗證了「靜音量得準」。
5. 沒有和現在的 gTTS 做並排比較（速度、音色、清晰度）。
