# E4 實驗報告：教案的 `{…}` 表達式，能在紀錄上求值嗎？

日期：2026-09-25　性質：throwaway 實驗　環境：Node 20

## 結論（一句話）

**Go。** 教案用的表達式語言非常小（只有「變數」和「索引」兩種形狀），我們自己寫的求值器在紀錄快照上算，跟 GDB 自己求值的結果**在 1,456 次求值中 1,453 次完全一致（99.79%）、0 次不一致**；另外 3 次「求不出來」的其實是 GDB 讀到垃圾值、我們的行為更正確。前端另外會用到的 vector 容量（`.capacity()`）也能由探針提供，1,979 次比對全部一致。

## 1. 教案裡實際用到什麼表達式

全部 23 份教案（`e4_extract.mjs`）：**406 個 `{…}` 標記，只有 69 種不同的表達式，只有兩種形狀**：

| 形狀 | 種類 | 例 |
| --- | --- | --- |
| 單純變數 | 38 | `row`、`w`、`best`、`dp` |
| 索引（索引裡可含簡單加減） | 31 | `table[i][w]`、`weights[i - 1]`、`dp[r][j + 1]` |

**沒有任何函式呼叫、成員函式、取址、比較、三元運算。** 標記也出現在 `@tts`（134 個）。

## 2. 求值器（`evalexpr.mjs`）

不執行任何程式碼，只在快照（變數名 → JSON 值）上算。支援：數字、變數、索引 `a[i][j]`、`size()`／`empty()`／`back()`／`front()`、`capacity()`（查偽變數）、`+ - * / %`、比較、邏輯、三元、括號。求不出來時丟出帶分類的錯誤（`undefined`、`oob`、`type`、`unsupported`…）。

**全部 69 種表達式都能解析**（`e4_parse_all.mjs`：沒有語法錯誤或不支援的種類）。

## 3. 對照 GDB 自己求值（標準答案）

GDB 參考腳本在每個停駐點，對「該行標註裡的每個表達式」用 `parse_and_eval` 求值；GDB 對這四份教案的全部 1,456 次求值**全部成功，0 次失敗**（連 `std::vector` 的二維索引都能算）。

| 教案 | 求值次數 | 一致 | 不一致 | 我們求不出來 |
| --- | --- | --- | --- | --- |
| 技巧一 | 467 | 467 | 0 | 0 |
| 技巧二（遞迴、全域變數） | 479 | 476 | 0 | **3** |
| 走方格 AtCoder | 273 | 273 | 0 | 0 |
| 走方格 DP 推導 | 237 | 237 | 0 | 0 |
| **合計** | **1,456** | **1,453（99.79%）** | **0** | **3** |

### 那 3 次「求不出來」

全部是**同一種情況**：技巧二第 52 行 `for (int j = 0; j < w; ++j)` 的標註引用了 `{j}`，而 3 次都發生在「剛進入這個迴圈、`j` 還沒宣告」那一站。GDB 讀到的是堆疊上殘留的舊值（0、3、3），我們說「`j` 不在作用域內」。**GDB 的答案其實是垃圾值，我們的行為更正確**；這是教案標註的小瑕疵（在迴圈那一行引用迴圈變數）。

### 需要注意的細節

- **char 與 string**：快照裡 `char` 和 `std::string` 都是字串，GDB 對 `char` 給整數字元碼。有 96 次比對靠「長度 1 的字串當作字元碼」才一致。正式版的探針應該記錄變數的型別（AST 有 `qualType`），求值器才能分清楚。
- **整數除法**：快照沒有型別，`a / b` 只能用「兩邊都是整數就截斷」猜；教案目前沒有用到除法，但正式版需要型別才能保證跟 C++ 一致。
- **索引越界**：我們回報錯誤；GDB 會讀到範圍外的記憶體、不報錯（垃圾值）。教案沒有這種寫法。

## 4. 前端額外向 GDB 要的「輔助表達式」

現有前端為每個標記背後還會建立一些額外的 GDB 表達式，「假 GDB」也得回應：

| 輔助表達式 | 用途 | 結論 |
| --- | --- | --- |
| 索引的子表達式（`r`、`j + 1`） | 分別求值後算出要亮哪一格 | ✅ 求值器已涵蓋 |
| 容器本身（`dp`） | 畫容器 | ✅ 快照就有 |
| **`&(expr)`**（取址） | 前端會建立它，但**整個專案沒有任何地方讀取它的值**（`VisualizerHelper.js:890-896` 只有建立） | 死程式碼，不必提供 |
| **`x.capacity()`** | **`std::vector` 的容量，容器視覺化用它畫「超出長度的空格子」（`LinearPlugin`／`ContainerVisualizer`）；只對 `std::vector` 啟用** | ✅ 探針記錄成偽變數 `x.capacity()`，見下 |

### vector 容量（`.capacity()`）

- 探針對每個 `vector` 變數多記一個偽變數 `x.capacity()`；GDB 端直接讀 libstdc++ 的成員（結尾指標 − 起始指標，不呼叫函式）。
- **比對 1,979 次，全部一致**（另有 135 次是變數尚未宣告，GDB 讀到殘留記憶體，不該比）。
- **libc++（我們）vs libstdc++（GDB／GCC）的容量行為**（`cases/capacity.cpp`，兩邊各編一次比對，49 行輸出）：
  - **相同**：`push_back` 連續成長、`vector(n)`、`vector(n, v)`、初始化列表、`reserve`、`clear`、`shrink_to_fit`、`assign`、複製／移動、二維 vector。
  - **不同**：`resize(12)`（GCC 12、libc++ 20）、`insert` 5 個超過容量（GCC 9、libc++ 12）——成長策略不同。
  - `string` 的容量完全不同（GCC 15→30→60，libc++ wasm32 是 10→23→47），但**前端只對 `std::vector` 顯示容量**，所以不影響畫面。
  - 現有教案只用到 `assign`（兩邊相同），**不受影響**。

## 沒做／沒驗證的

1. **只有 4 份教案有 GDB 的標準答案。** 其餘 19 份的表達式用同樣的兩種語法，我只驗證了「能解析」，沒有逐站對照結果。
2. 沒測 `@tts` 裡 `[fast @{n}]` 這類「在迴圈前求值」的用法（同樣用求值器，應該沒問題）、呼叫圖標籤、`uml:` 這些前端別的地方用到的名稱。
3. 探針記錄的容量是我們的 libc++ 的實際值，在 `resize`／`insert` 之後可能跟學生在本機用 GCC 看到的不同；目前教案沒有這種寫法。
4. 型別資訊（char／string、int／double）還沒進紀錄，見上。
5. 還是 Node 環境，不是瀏覽器。

## 對正式設計的意義

- 求值器可以很小、很安全（不執行程式碼），教案表達式語言不必擴充。
- 紀錄要加上**每個變數的型別**（來自 AST），才能保證字元、整數除法與 C++ 一致。
- 「假 GDB」不需要提供取址；需要提供 `vector` 的容量。
- 教案作者要避免在 `for` 標頭那一行引用迴圈變數（新舊系統行為不同，舊系統顯示垃圾值）。
