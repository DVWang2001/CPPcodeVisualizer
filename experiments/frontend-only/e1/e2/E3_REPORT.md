# E3 實驗報告：效能與安全上限

日期：2026-09-25　性質：throwaway 實驗　環境：**Node 20（不是瀏覽器）**，本機 Windows 11

## 結論（一句話）

**E3 的三項標準都通過，但有條件**：時間標準要靠預編譯標頭（PCH）才達到；記憶體峰值偏高（約 0.9 GB）；所有數字都是 Node 量的，瀏覽器實測還沒做。

| 標準 | 門檻 | 結果 | 判定 |
| --- | --- | --- | --- |
| 技巧一 5×4，從按下 Run 到拿到完整紀錄（熱） | ≤ 3 秒 | 無 PCH 約 3.9 秒；**有 PCH 約 2.8 秒** | ✅ 有條件（需 PCH，見下） |
| 走方格 8×8、背包：紀錄大小 | ≤ 20 MB | 走方格 8×8：33 KB；背包：約 29 KB（差量編碼前） | ✅ |
| 無窮迴圈 ≤ 2 秒終止、不凍結分頁 | ≤ 2 秒 | 有探針 0.64 秒（步數上限）；完全沒有探針 → Worker 逾時終止 | ✅ |

## 1. 22 個案例的基準（`e3_bench.mjs`）

技巧一／技巧二／走方格（放大輸入）、DP 課 1～5、Dijkstra、堆疊、雙端佇列、字串、串列、向量排序等，**全部能插樁、編譯、正確執行，沒有遇到任何不支援的語句**。

| 案例 | 步數（合併後） | 紀錄大小（差量前 → 後） | 執行 |
| --- | --- | --- | --- |
| 技巧一 5×4 | 382 | 112 KB → 45 KB | 26 ms |
| 技巧一 10×10 | 1,974 | 1.7 MB → 307 KB | 126 ms |
| 技巧一 **20×20** | 8,084 | **25.0 MB → 2.4 MB** | 1.09 秒 |
| 技巧二 8×8 | 2,473 | 1.2 MB → 286 KB | 125 ms |
| 技巧二 12×12 | 5,625 | 5.5 MB → 712 KB | 365 ms |
| 走方格 AtCoder 8×8 | 344 | 117 KB → 33 KB | 28 ms |

- 每個案例的「AST 分析＋編譯」都約 4 秒（冷，每次重新載入編譯器），與教案大小、步數無關；**時間主要花在編譯器本身**，不是花在使用者程式。
- 各教案的行數 11～71，步數 7～8,789。

## 2. 紀錄大小：差量編碼（重要）

原本每一步都把作用域內所有容器整個重新輸出，大小是「步數 × 容器大小」：技巧一 20×20 有 25 MB，超過門檻。改成**差量編碼**：探針只輸出「跟上次不同的變數」，另外列出目前在作用域內的變數名；解碼端用同樣規則還原完整快照。

- 大小縮小 **約 10 倍**（25.0 → 2.4 MB；5.5 → 0.7 MB）。
- 回歸：五個程式與正式機 GDB 的比對**仍然全部一致**（共 8,371 筆，0 不一致）。
- 沒解決的：探針仍要把每個變數序列化才能比較，是 O(容器大小)／步；20×20 的執行時間因此是 1.09 秒（原程式只要幾毫秒）。正式版可以只記錄教案標註實際引用的變數。

## 3. 時間：預編譯標頭（PCH）與實例重用

重複量測 5 次取中位數（單次很吵，V8 有暖機）：

| 階段 | 無 PCH | 有 PCH（常用 6 個標頭） | 差異 |
| --- | --- | --- | --- |
| AST 分析 | 1.10 秒 | 0.74 秒 | −33% |
| 編譯＋連結 | 2.8 秒（1.6～2.9，很不穩） | 2.06 秒（很穩） | −26% |
| **合計** | **約 3.9 秒** | **約 2.8 秒** | 達到 ≤ 3 秒 |

- PCH 是我們自己用同一個 wasm clang 建的（`pch.mjs`，約 1.5 秒），輸出與無 PCH 完全一致。
- PCH 大小：常用標頭版 15.4 MB（brotli 後 **6.2 MB**）、完整 `bits/stdc++.h` 版 21.3 MB（brotli 後 **8.5 MB**）；**每個 C++ 標準要一份**（`-std` 必須相同）。加到 E1 的下載預算約 20.6 → 27 MB，仍遠低於 60 MB 目標。
- **重用已編譯的 `WebAssembly.Module`**：建立 Clang 實例從 117 ms 降到 **10 ms**（一次 Run 有 3 個實例：AST、編譯、連結，約省 0.3 秒）。瀏覽器可以把編譯好的 Module 快取起來。
- **PCH 的語意風險**：PCH 會讓「使用者沒有 `#include` 的標頭」的名稱也可見。若學生程式自己定義了跟標準函式庫同名的全域函式（如 `gcd`、`next`、`count`），又有 `using namespace std;`，可能出現在 GCC 上沒有的名稱衝突。緩解：對每個「使用者的 `#include` 組合」各建一份 PCH 並快取（首次多 1.5 秒）；或部署時針對已知教案預先建好。
- 沒有做：把 AST 分析與編譯平行化（有相依，不能），或自己寫輕量解析器取代 AST 分析。

## 4. 失控程式的安全上限（`t_guard.mjs`）

兩層防護：**探針層**（`vg.h` 內：步數 > 20 萬 或 輸出 > 20 MB 就標記 `VGLIMIT` 並 `exit(124)`）＋ **Worker 層**（外部計時器 `terminate()`）。

| 案例 | 結果 | 耗時 |
| --- | --- | --- |
| `while (true) { x++; }` | 探針上限中止（紀錄 9 MB） | 0.64 秒 |
| `for (;;) {}`（完全沒有探針） | **Worker 逾時被終止** | 2.0 秒（＝逾時設定值） |
| 無窮遞迴 | WebAssembly 堆疊溢位，trap（`memory access out of bounds`） | 0.04 秒 |
| 合法的 10 億次迴圈 | 探針上限中止 | 0.9 秒 |
| 一次配置 40 億個 `int` | `bad_alloc` → `abort`（trap `unreachable`） | 0.04 秒 |
| 正常程式 | 正常結束，輸出 `4950` | 0.04 秒 |

- **`for(;;){}` 這種沒有任何探針的迴圈，只能靠 Worker 計時器**；因此正式版一定要在 Worker 裡執行編譯後的程式（本來就該如此，不然學生的程式會凍結整個分頁）。逾時值是政策：建議 1.5 秒起跳、可讓使用者延長。
- trap 的錯誤訊息對使用者不友善（`memory access out of bounds` 其實是堆疊溢位、`unreachable` 是記憶體不足或 `abort`），正式版要翻譯。
- **合法但很長的計算會被步數上限擋下**（例如 10 億次迴圈）。教學視覺化本來就不適合，但要有「不記錄、直接執行」的模式，否則這類程式無法跑完。

## 5. 記憶體

- Node 行程 RSS 峰值約 **900 MB**（起始 119 MB；三個 clang／lld 實例同時存活時）。技巧一 5×4 與 20×20 幾乎一樣，代表主要是編譯器本身，不是使用者程式。
- 這比 E1 只量「增量」的 293 MB 高得多。瀏覽器每個分頁通常允許 2～4 GB，一般筆電可以，但**較舊或記憶體小的學生筆電是風險**，尚未實測。
- 可能的緩解：每個階段結束就釋放該實例（讓 GC 回收），AST 與編譯不要同時持有。

## 沒做／沒驗證的

1. **全部是 Node 的數字**。瀏覽器的冷啟動（下載並編譯 43 MB 的編譯器與 PCH）、Worker 內的實際速度、記憶體上限、Firefox／Safari 都沒測。
2. PCH 與「實例重用」只在單獨的量測腳本裡驗證，**沒有整合進 `trace.mjs` 的完整流程**；2.8 秒是把兩階段的中位數相加，不是端到端量的。
3. 沒測 C++20／23 下的 PCH 與 `bits/stdc++.h` 完整版 PCH 的端到端時間。
4. 較舊筆電的實測數字。

## 對正式設計的意義

- 「按 Run 到出畫面」約 3 秒是可行的，但**不是即時**；比現在伺服器編譯（`g++` 約 1 秒）慢。要用進度提示、把編譯器預先載入並暖機來掩蓋。
- 必須有：Worker 執行、逾時終止、步數上限、錯誤訊息翻譯、「不記錄直接執行」模式。
- 記憶體與 PCH 語意衝突是兩個要在瀏覽器實測時優先確認的風險。
