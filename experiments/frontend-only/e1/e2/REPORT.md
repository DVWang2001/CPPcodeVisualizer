# E2 實驗報告：原始碼插樁的逐行記錄，和 GDB 對得上嗎？

日期：2026-09-25　性質：throwaway 實驗　環境：Node 20（瀏覽器實測尚未做）

## 結論（一句話）

**Go。** 用 clang 的 AST 做原始碼插樁，在瀏覽器端的編譯器（E1）上執行，得到的「停駐行序列」與「區域變數值」，對四份真實教案都**與正式機的 GDB 完全一致**：行序列 4/4 份逐步相同，共 5,578 筆（停駐點 × 變數）比對，0 筆不一致。

## 結果

| 教案 | 程式特徵 | GDB 模式 | 停駐點數 | 行序列 | 變數值比對 |
| --- | --- | --- | --- | --- | --- |
| 技巧一 | 三層巢狀 for、if、`return`、`vector<vector<int>>` | `next` | 372 | ✅ 完全相同 | 3,394 筆，0 不一致 |
| 技巧二 | **遞迴**（`solve` 呼叫自己）、記憶化、全域變數 | `step`（只進入使用者函式） | 333 | ✅ 完全相同（含函式名稱） | 1,219 筆，0 不一致 |
| 走方格 AtCoder | `continue`、`vector<string>`、巢狀 for | `next` | 79 | ✅ 完全相同 | 460 筆，0 不一致 |
| 走方格 DP 推導 | 同上 | `next` | 87 | ✅ 完全相同 | 505 筆，0 不一致 |

- **插樁不改行號**：四份教案插樁前後行數完全相同（71／66／39／46）。
- **程式行為不變**：插樁後的程式輸出與原程式相同（例如技巧一仍輸出 `3 2 2 1` ／ `6`）。
- 重點行（技巧一第 34、48、51、57 行等，共 22 站）與其他抽樣行都在比對範圍內，0 不一致。
- 參考答案來自正式機的 GDB 16.3 ＋ g++ 14.2，用與正式服務相同的旗標編譯（`-g -O0 -no-pie`）。

## 方法

1. **AST**：用 E1 的 clang（WebAssembly 版）`-ast-dump=json` 取得函式的語法樹，只取主檔案的函式（`main` 約 0.7 MB、1.7 秒）。
2. **插樁**：只做「插入」，不改行號；每個 GDB 會停的位置前面插入 `__vg::step(行號, 函式名, {變數…})`，`vg.h` 把變數與容器（只靠 `begin()`／`end()` 走訪）序列化成 JSON，寫到 stderr。
3. **記錄**：在 WASI 裡執行，收集 stderr 中前綴 `\x01VG` 的行。
4. **參考**：在正式機容器內用 GDB 的 Python 介面逐步 `next`（或 `step`），記錄行號、函式、區域變數（`gdbref.py`）。

### 從實測歸納出、GDB（gcc -O0）的停駐規則

| 語句 | 停駐規則 |
| --- | --- |
| 沒有初值的宣告（`int h, w;`） | **不停**（沒有機器碼） |
| 有初值的宣告、運算式、`break`、`continue` | 停一次，在這一行**執行前** |
| `for (init; cond; inc)` | 進入時停一次（init 之前）；之後**每次遞增**再停一次；條件判斷與遞增同一行，不多停 |
| `while` / `if` / `else if` | 每次求值條件停一次 |
| `return X;` | 先停在 `return` 那行，X 算完後**停在函式的 `}`** |
| 函式正常結束（沒有 return） | 停在 `}` |
| **同一行有多個語句**（例如 `best = …; bestRow = r;`） | **只算一站**：GDB 只在「行號改變」時才停。這是第一次比對時抓到的差異（我們多停了一站），修正後全部一致。 |

## 沒涵蓋、要知道的限制

1. **只驗證了 4 份教案**（共 23 份）。插樁器對下列語句會直接報錯，**尚未支援**：範圍 for（`for (auto x : v)`，現代 C++ 很常見）、`switch`、`do-while`、`goto`、`try`。類別／成員函式、lambda、樣板函式、結構化綁定也沒測。
2. **沒有初值的變數排除在比對外**（GDB 在賦值前顯示垃圾值，不可能對得上）：技巧二的 `result` 有 267 筆被排除，其餘教案各 2 筆。所以賦值之後的正確性，這裡沒有逐站驗證。
3. **只記錄區域變數與參數，沒有記錄全域變數。** 技巧二的 `h`、`w`、`a`、`dp` 都是全域，教案標註的 `{dp}` 就是引用全域變數。正式版的探針必須記錄「教案標註用到的全域變數」，否則視覺化沒有資料。這是 E4 之前必須處理的。
4. **只比對了「停駐點」的序列與值**，沒有測「假 GDB」本身（`continue`、斷點、`finish`、`step` 進出、反向）。這些在有完整紀錄的前提下應該只是邏輯，但還沒做。
5. `step` 模式的參考是**跳過標準函式庫**的（`skip -gfi /usr/include/c++/*`）。目前正式系統沒有這個設定，`[step-in]` 若用在含標準函式庫呼叫的行上，GDB 會踏進 `std::vector` 內部（技巧二的參考在沒跳過時是 1,694 步，跳過後 333 步）。教案目前只在呼叫自己寫的函式的那一行用 `[step-in]`，所以不影響，但這是現有行為，新系統要決定是否沿用。

## 效能（Node，冷啟動）

- 取 AST 每個函式約 1.7 秒（技巧二有 `main`、`solve` 兩個函式，約 3 秒），編譯約 2.3 秒，**執行 ≤ 21 毫秒**。所以一次「按 Run」約 4～5 秒，其中一半是為了取 AST。
- 可以優化：只取一次 AST（不逐函式篩選）、或改用自己的輕量解析器；正式版前要處理。
- 執行紀錄大小：技巧一 395 個事件、約 98 KB JSON；其餘教案 10～25 KB。E3 才會量大型教案。

## 下一步的判斷

E2 過關，可以進 E3（大型教案的效能與步數上限）與 E4（教案的 `{…}` 表達式能否在紀錄上求值）。E4 會用到限制 3（全域變數）。**範圍 for 建議在進入正式設計之前補上**，因為學生程式碼裡很常見。

## 如何重現

見同資料夾 `README.md`。腳本：`instrument.mjs`（插樁）、`trace.mjs`（編譯執行並收集）、`gdbref.py`（GDB 參考）、`compare.mjs`／`compare_values.mjs`（行序列／變數值比對）；`ref/` 是正式機 GDB 擷取的參考答案與輸入。
